# Feature #7: Модель данных v1 и миграции Alembic

## Обзор
Первая версия схемы PostgreSQL 16 для прототипа (этап 1) и инфраструктура БД: Alembic в async-режиме, async-сессия SQLAlchemy 2, базовый класс моделей с соглашением об именах ограничений, тестовая фикстура `db`. Схема покрывает заведение (`tenants`, `halls`, `tables`), меню (`categories`, `menu_items`, `menu_item_prices`, `menu_item_meta`, `allergens`, `menu_item_allergens`), визит (`visits`, `messages`, `cart_items`) и заказ (`orders`, `order_items`, `order_events`) по ТЗ, раздел 7. Правила: `tenant_id` во всех таблицах заведения, деньги `NUMERIC(10,2)`, время `timestamptz`, позиции меню связываются с кассой по `external_id` и никогда не удаляются (скрываются), заказ сохраняется до любого вызова ИИ. Дополнительно: сид-данные для разработки и проверка обратимости миграций в CI. Каркас (#6) уже в main: есть `DATABASE_URL` в настройках, маркер pytest `db` и Linux-джоб CI с postgres.

Архитектурные решения (ERD, ADR) — в `docs/arch/feature-7-data-model.md` (пишет architect). Имена таблиц совпадают с ТЗ, раздел 7.

## Functional Requirements
- FR-1: Alembic (каталог `backend/alembic/`) настроен для async-драйвера (`postgresql+asyncpg`), адрес БД берётся только из `DATABASE_URL`; все миграции обратимы (`upgrade` / `downgrade` / `upgrade`). Story #48. (ТЗ раздел 7: «Миграции — Alembic»; ТЗ NFR-8, раздел 9.2)
- FR-2: приложение получает async-сессию SQLAlchemy через единую фабрику; общий базовый класс моделей задаёт соглашение об именах ограничений, миксины `tenant_id` и `created_at`/`updated_at`. Story #48. (ТЗ раздел 7, NFR-4)
- FR-3: тестовая фикстура `db` (маркер `db`, подключение только из `TEST_DATABASE_URL`, имя БД оканчивается на `_test`) готовит схему миграциями и изолирует тесты откатом транзакции. Story #48. (ТЗ раздел 9.2)
- FR-4: `tenants`, `halls`, `tables`; `qr_token` стола уникален глобально, `external_id` стола уникален в пределах заведения; тип стола и тариф цен хранятся как в ТЗ. Story #49. (ТЗ раздел 7, FR-1, FR-15, FR-21)
- FR-5: меню: `categories`, `menu_items`, `menu_item_prices`, `menu_item_meta`, `allergens`, `menu_item_allergens`; `external_id` уникален в пределах заведения; пропавшая из кассы позиция помечается `is_hidden`, не удаляется; данные кассы и данные админа (`menu_item_meta`) хранятся раздельно; флаг `allergens_verified` по умолчанию `false`. Story #50. (ТЗ раздел 7, раздел 4.4, INT-2, FR-3, FR-16, FR-16a, FR-17, AI-2)
- FR-6: `visits` (на столе не более одного открытого визита), `messages` (диалог в `jsonb`, вызовы функций, токены `input`/`output`/`cache_*`, `cost_usd`, `latency_ms`, `redacted_at`), `cart_items` (одна текущая корзина визита, позиции с разным комментарием раздельны, цена на момент добавления). Story #51. (ТЗ раздел 7, FR-5, FR-7, FR-14a, INT-3, NFR-5)
- FR-7: `orders` (уникальный `idempotency_key`, статусы жизненного цикла с CHECK), `order_items` (снимок названия и цены, `removed_by_staff`), `order_events` (журнал изменений). Story #52. (ТЗ раздел 7, раздел 4.6, FR-6, FR-9, FR-13, NFR-3, INT-3, INT-5..INT-7)
- FR-8: сид-данные для разработки: вымышленное заведение, зал, столы, меню на AZ/RU, справочник аллергенов, визит, заказ; команда идемпотентна и недоступна в `prod`. Story #53. (ТЗ раздел 7, FR-15, FR-16a)
- FR-9: CI проверяет цикл `upgrade` / `downgrade` / `upgrade`, отсутствие расхождения моделей с миграциями (`alembic check`) и инварианты схемы (`tenant_id`, `NUMERIC(10,2)`, `timestamptz`) тестом на реальной БД. Story #54. (ТЗ раздел 7, NFR-4, quality gate G4)

## Non-Functional Requirements
- NFR-1 Мультиарендность (ТЗ раздел 7, NFR-4): `tenant_id` NOT NULL с индексом во всех таблицах заведения; уникальные ограничения с `external_id` и именами включают `tenant_id`; родительские таблицы имеют `UNIQUE (tenant_id, id)`, ссылки на них — составные внешние ключи `(tenant_id, x_id)`, поэтому межарендная ссылка отклоняется самой БД (arch ADR-7.3). Таблицы без `tenant_id`: только `tenants` и служебная `alembic_version`.
- NFR-2 Деньги и время (ТЗ раздел 7): денежные суммы `NUMERIC(10,2)` в БД, `Decimal` в коде; время `timestamptz`, в коде только aware-datetime (в `ruff` включено правило `DTZ`). Исключение — `messages.cost_usd` (стоимость токенов в долях цента, ТЗ NFR-7): `NUMERIC(12,6)`, исключение перечисляется явно в тесте инвариантов.
- NFR-3 Надёжность заказа (ТЗ NFR-3): заказ и его позиции записываются в БД до любого вызова ИИ; повторная отправка с тем же `idempotency_key` не создаёт второй заказ (ограничение уникальности на уровне БД).
- NFR-4 Обратимость и повторяемость: каждая миграция имеет рабочий `downgrade`; цикл `upgrade` / `downgrade base` / `upgrade` проходит на пустой БД; имена ограничений и индексов детерминированы (соглашение об именах).
- NFR-5 Переносимость (ТЗ NFR-8, раздел 9.2): конфигурация только через `DATABASE_URL`; в коде, миграциях и сидах нет абсолютных путей, IP-адресов, ОС-специфики; тесты схемы работают на PostgreSQL 16 как службе Windows (без Docker) и на сервис-контейнере CI. В режиме `single` схема та же, Redis для БД не нужен.
- NFR-6 Безопасность (ТЗ NFR-4, NFR-5): токены и секреты в сидах не боевые, сид запрещён при `APP_ENV=prod`; в схеме нет персональных данных гостя (гость анонимен); ключи коннекторов и хеши PIN в #7 не создаются.
- NFR-7 Целостность данных кассы (ТЗ INT-2): строки `categories`, `menu_items` не удаляются приложением; внешние ключи на них `RESTRICT`.
- NFR-8 Хранение диалогов (ТЗ NFR-5, раздел 3.4 `dialog_retention_days`): у `messages` есть индекс по `(tenant_id, created_at)` для будущей очистки по сроку.
- NFR-9 Качество: `ruff` и `pytest` без ошибок, покрытие нового кода ≥ 95%, unit-тесты без БД укладываются в 2 минуты; тесты с БД выполняются в Linux-джобе CI с postgres.

> Нумерация FR/NFR в spec — локальная для фичи; рядом указан исходный пункт ТЗ.

## Acceptance Criteria (Given / When / Then)
### AC-1 (story #48)
**Given** задан `DATABASE_URL` на пустую базу PostgreSQL 16 и установлены зависимости `sqlalchemy[asyncio]`, `asyncpg`, `alembic`
**When** выполняются `alembic upgrade head`, `alembic downgrade base` и `pytest -m db` с пробным тестом на фикстуре `db`
**Then** команды Alembic завершаются без ошибок, тест проходит, его данные не остаются в базе, а отсутствие `DATABASE_URL` даёт понятную ошибку без показа пароля

### AC-2 (story #49)
**Given** применена миграция `tenants`, `halls`, `tables`, вставлено заведение
**When** добавляются столы с повторяющимся `qr_token` и повторяющимся `external_id` (в том же и в другом заведении)
**Then** повтор `qr_token` и повтор `external_id` внутри заведения отклоняются, тот же `external_id` в другом заведении принимается, недопустимый `type` и ссылка на зал другого заведения отклоняются (CHECK и составной внешний ключ), `downgrade -1` удаляет три таблицы

### AC-3 (story #50)
**Given** применена миграция меню, в заведении есть позиция с `external_id = '157'`, ценами `default` и `vip`, и `menu_item_meta`
**When** добавляется позиция с тем же `external_id`, вторая цена того же тарифа, такая же позиция в другом заведении и выставляется `is_hidden = true`
**Then** дубли внутри заведения отклоняются, в другом заведении принимаются, ссылка на категорию другого заведения отклоняется, связанные данные после скрытия сохраняются, отрицательная цена и `spice_level` вне 0..3 отклоняются, `allergens_verified` по умолчанию `false`

### AC-4 (story #51)
**Given** применена миграция визитов, есть стол и позиции меню
**When** на столе открывается визит, затем второй открытый визит, затем в корзину дважды добавляется позиция с пустым комментарием и ещё раз с комментарием, затем визит закрывается и открывается новый
**Then** второй открытый визит и повтор строки корзины с тем же комментарием отклоняются, строка с другим комментарием принимается, `qty` вне 1..99 и недопустимые `status`, `lang`, `closed_by` (допустимы `staff`/`pos`/`timeout`), роль сообщения отклоняются, после закрытия новый визит открывается

### AC-5 (story #52)
**Given** применена миграция заказов, у открытого визита есть заказ с `idempotency_key = 'k1'` и две позиции
**When** вставляется заказ с тем же ключом, статус меняется на неизвестный, затем на `confirmed`, записывается событие
**Then** повтор ключа и неизвестный статус отклоняются, допустимы ровно 8 статусов жизненного цикла, позиции хранят снимок названия (`pos_name`) и цены, событие связано с заказом и не может быть изменено или удалено (триггер)

### AC-6 (story #53)
**Given** применены все миграции на пустой базе
**When** сид запускается дважды
**Then** после первого запуска есть полный демонстрационный набор вымышленных данных, после второго количество строк не меняется, в данных нет IP-адресов и секретов, при `APP_ENV=prod` сид отказывается работать

### AC-7 (story #54)
**Given** Linux-джоб CI с postgres и все миграции #7
**When** выполняются `upgrade head`, `downgrade base`, `upgrade head`, `alembic check` и тест инвариантов схемы
**Then** все команды завершаются с кодом 0; нарушение любого инварианта (`tenant_id`, `NUMERIC(10,2)`, `timestamptz`) или рассинхрон моделей и миграций делает джоб красным

## Открытые вопросы
Статус «принято» означает решение architect в `docs/arch/feature-7-data-model.md` (ADR-7.x); stories #48–#53 приведены в соответствие с ним. Вопросы 1–24 — из анализа, 25–38 — добавлены architect (нумерация здесь сквозная; в arch doc они идут как вопросы 1–16 отдельной таблицы, одноимённые объединены).

### Вопросы анализа (решения приняты)
1. **Тип первичного ключа.** Было: `bigint`, `orders.id` — uuid. Принято: UUIDv7 во всех таблицах с суррогатным ключом, генерирует приложение (`new_id`), запасной `gen_random_uuid()`; связки (`menu_item_prices`, `menu_item_allergens`) и `menu_item_meta` — с натуральным или общим PK (ADR-7.1). Причина: ID виден анонимному гостю, возможно слияние БД при переносе на VPS, `orders.id` всё равно uuid. Следствие: `confirmed_by.staff_id: 7` в примере ТЗ 4.4 станет UUID-строкой (вопрос 25).
2. **Защита межарендных связей в БД.** Было: без составных FK. Принято: у родителей `UNIQUE (tenant_id, id)`, ссылки — составные FK `(tenant_id, x_id)`; межарендная ссылка отвергается БД (тест `test_tenant_isolation.py`, ADR-7.3); RLS — будущая опция.
3. **Уникальность `external_id`.** Принято как рекомендовано: `text`, `UNIQUE (tenant_id, external_id)` для `categories`, `menu_items`; для `tables` только где значение не NULL.
4. **Валюта.** Принято: `tenants.currency` (настройка), `menu_items.currency` (из кассы), `orders.currency` (снимок), `text CHECK (currency ~ '^[A-Z]{3}$')`; синхронизация отклоняет позиции с валютой, отличной от валюты заведения (вопрос 38).
5. **`price_tier`.** Принято: `text` с CHECK формата, без справочника, `default` обязателен, резерв — `default`.
6. **Статусы.** Принято: `text` + именованный `CHECK`, не enum PostgreSQL (ADR-7.2); значения CHECK сверяются с `StrEnum` тестом.
7. **Soft-delete.** Принято: не вводить; `is_hidden`, `is_active`, перевыпуск токена.
8. **Токены и стоимость сообщений.** Было: `tokens_in`, `tokens_out`, `cost`, `tool_calls`. Принято: `input_tokens`, `output_tokens`, `cache_read_tokens`, `cache_creation_tokens` (как `usage` Claude API), `cost_usd NUMERIC(12,6)` (явное исключение из правила `NUMERIC(10,2)`), `content jsonb` (полные блоки, включая tool_use и tool_result), `model`, `latency_ms`, `redacted_at` (ADR-7.4).
9. **Корзина.** Принято: `price_at_add NUMERIC(10,2)` и `price_tier` добавлены (нужны для INT-3); `comment text NOT NULL DEFAULT ''` и `UNIQUE (visit_id, menu_item_id, comment)`.
10. **Тип количества.** Было: `NUMERIC(10,3)`. Принято: `integer` с CHECK от 1 до 99 в корзине и заказе (Integration API всё равно передаёт `qty` строкой; переход на `NUMERIC(10,3)` — одна миграция, вопрос 28).
11. **Один открытый визит на стол.** Принято: частичный уникальный индекс `uq_visits_open_table`. Значения `visits.closed_by`: `staff`/`pos`/`timeout` (было `waiter`; закрыть визит может и администратор).
12. **FK на `staff_users` без таблицы.** Принято: `confirmed_by_staff_id`, `closed_by_staff_id` — `uuid` без FK, `order_events.actor_id` — `uuid`, мягкая ссылка; FK добавляет миграция #19 (ADR-7.7).
13. **Состав #7.** Принято: `staff_users` (#19), `connectors` (#16), `waiter_calls` (#22), `reviews` (#25) вне #7.
14. **Статус `edited`.** Принято: значение `orders.status` (8 статусов); переходы проверяет сервис (вопрос 33 — `escalated → edited`).
15. **`idempotency_key`.** Принято: `UNIQUE (tenant_id, idempotency_key)`.
16. **Справочник аллергенов.** Принято: на заведение, `sort_order`, копия 14 стандартных аллергенов ЕС при создании заведения; названия AZ проверить носителем.
17. **Вес блюда.** Принято: `weight_amount NUMERIC(8,2)` + `weight_unit` (`g`/`ml`/`pcs`).
18. **Состав `tenants`.** Принято: `timezone` IANA, `languages text[]`, `settings jsonb` только с переопределениями порогов (ADR-7.14); без `slug`, `is_active`.
19. **Проверка БД в `/health`.** Принято: **проверка БД в `/health/ready` — отдельная story после #48, не в #7** (спроектирована в ADR-7.9, поле `database`).
20. **Подготовка БД для тестов.** Принято: `TEST_DATABASE_URL` (имя БД оканчивается на `_test`, никогда `DATABASE_URL`), схема из миграций, изоляция откатом (savepoint); без переменной локально `skip`, при `CI=true` ошибка (ADR-7.11).
21. **`created_at`/`updated_at`.** Принято: везде, кроме журналов (`messages`, `order_events`: только `created_at`); у `visits` — `opened_at` + `updated_at`; триггеры БД для `updated_at` не используются.
22. **Хранение `qr_token`.** Принято: открытым текстом (`UNIQUE`), защита — отзыв и перевыпуск, подтверждение заказа официантом.
23. **`order_items.name_snapshot`.** Было: название на языке визита. Принято: `menu_items.pos_name` на момент заказа (официант без `push_order` вводит заказ по кассовому названию); локализованное имя гостю берётся из `menu_item_meta`.
24. **Каталог миграций.** Было: `backend/migrations/`. Принято: `backend/alembic/` и `backend/alembic.ini` без URL; ревизии с ручными ID `0001_tenants_tables` (#49), `0002_menu` (#50), `0003_visits` (#51), `0004_orders` (#52); `order_events` append-only через триггер в `0004` (ADR-7.6, ADR-7.10).

### Вопросы, добавленные architect (рекомендации arch doc)
25. **`staff_id` в примере ТЗ 4.4** (`confirmed_by.staff_id: 7`) — целое, а ключи UUID. Рекомендация: поправить пример ТЗ на UUID-строку.
26. **Несколько телефонов за одним столом.** Рекомендация: общий визит, корзина и журнал `messages`; язык ответа по последнему сообщению (AI-6); раздельные чаты — `messages.device_id` в #9, если понадобится.
27. **Кто открывает визит** (ТЗ 13.8). Рекомендация: первое сканирование QR открывает визит автоматически; режим «визит открывает официант» — позже настройкой в `tenants.settings`.
28. **Дробные количества** (полпорции, на вес). Рекомендация: v1 — целые 1..99; переход на `NUMERIC(10,3)` — одна миграция.
29. **Обезличивание вместо удаления диалогов** (`dialog_retention_days`). Рекомендация: `text`/`content` → NULL и `redacted_at`; токены и стоимость сохранять для метрик раздела 11.
30. **Сортировка по `sort_key`** (строка цифр кассы). Рекомендация: хранить строкой, сортировать `COLLATE "C"`; коннектор даёт ключи фиксированной ширины.
31. **Столы кассы из `PUT /tables` до сопоставления.** Рекомендация: отдельная таблица `pos_tables` в #16; `tables.external_id` — результат сопоставления админом.
32. **Владелец платформы.** Рекомендация: отдельная таблица `platform_users` без `tenant_id` (#16/#19), `staff_users.tenant_id` остаётся NOT NULL.
33. **Правка заказа в статусе `escalated`.** ТЗ 4.6 разрешает только `confirmed`/`rejected`. Рекомендация: разрешить `escalated → edited` (FR-13); до решения переходы следуют ТЗ буквально.
34. **Ручной ввод в кассу после `pos_failed`.** Рекомендация: статус остаётся, пишется событие `manual_pos_entry`.
35. **Пороги ТЗ 3.4 в `tenants.settings`.** Рекомендация: только переопределения (ADR-7.14).
36. **Теги блюд.** Рекомендация: свободный `text[]` в v1.
37. **Иерархия категорий.** Рекомендация: плоский список; `parent_id` — при подключении кассы с вложенными категориями.
38. **Валюта позиции отличается от валюты заведения.** Рекомендация: синхронизация отклоняет такие позиции с ошибкой коннектору.
