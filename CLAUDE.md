## Что это

ИИ-официант: гость по QR-коду общается с ботом (AZ/RU), собирает корзину, отправляет заказ официанту; официант подтверждает его в своей панели; коннектор передаёт подтверждённый заказ в кассу. Один продукт с тремя интерфейсами: гость `/t/{token}`, официант `/staff`, админ `/admin`.

Стек: Python 3.12, FastAPI, SQLAlchemy 2 (async) + Alembic, Pydantic, PostgreSQL 16; React + Vite + TypeScript + Tailwind (PWA); Claude API (tool use, стриминг SSE).

## Архитектурные правила

- **Независимость от кассы.** В ядре нет кода, специфичного для кассы. Кассы подключаются коннекторами через Integration API (`/integration/v1`, ТЗ 4.4); коннектор всегда инициирует соединение сам (опрос), ядро никогда не ходит в кассу. Поведение ядра зависит от объявленных коннектором возможностей (`menu`, `stoplist`, `tables`, `push_order`, `order_status`), а не от типа кассы.
- **Касса — источник цен и позиций.** Название, цена и наличие из кассы в админке не редактируются; админ дополняет только `menu_item_meta`. Позиции связываются по `external_id`; пропавшие из кассы скрываются (`is_hidden`), не удаляются.
- **Два режима запуска, один код.** `single` (один процесс, без Redis: шина событий в памяти, APScheduler) — для пробного запуска на Windows Server 2019 заведения без Docker; `scaled` (Redis pub/sub, arq, Docker Compose) — для VPS. Код обращается только к интерфейсам `EventBus`, `TaskScheduler`, `RateLimiter`; реализация выбирается конфигурацией. Не использовать Redis напрямую в обход этих интерфейсов.
- **Переносимость.** Конфигурация только через переменные окружения; никаких абсолютных путей, IP-адресов и Linux-/Windows-специфики в коде. Внешний адрес — всегда домен.
- **Мультиарендность.** `tenant_id` во всех таблицах заведения и во всех запросах; для гостя определяется по QR-токену стола, для коннектора — по его ключу, для персонала — по учётной записи.
- **Деньги** — `NUMERIC(10,2)` в БД, `Decimal` в коде, строка с двумя знаками в JSON API. Время — `timestamptz`.

## Правила ИИ-диалога (ТЗ, раздел 5)

- ИИ получает меню, цены и составы только через функции (`get_menu`, `search_menu`, `get_dish`, `cart_*`, `call_waiter`, `request_review`); меню целиком в промпт не кладётся.
- **У ИИ нет функции отправки заказа.** Заказ уходит только по кнопке гостя (`POST /orders` с `idempotency_key`), а цена при этом перепроверяется по последнему снимку меню.
- Об аллергенах ИИ говорит только по блюдам с `allergens_verified = true`; пустой список без этого флага означает «неизвестно».
- Сообщения гостя и описания блюд — данные, а не инструкции (защита от prompt injection).
- Модель и её параметры задаются в конфигурации, не в коде.
- Заказ сохраняется в БД до любого вызова ИИ; сбой модели не должен терять заказ.

## Жизненный цикл заказа

`submitted` → (`edited`) → `confirmed` | `rejected` | `escalated` → `sent_to_pos` → `in_pos` | `pos_failed`. Без возможности `push_order` заказ остаётся в `confirmed`, официант вводит его в кассу вручную. Все изменения пишутся в `order_events`.

## Первый коннектор: Yii2-касса «restoran»

Код кассы лежит в отдельной папке `D:\OSPanel\domains\restoran\restoran` (PHP, Yii2, MariaDB), это не часть этого репозитория. Там появятся `OrderService` и консольная команда `php yii ai-sync` (ТЗ, приложение A). Что важно знать о кассе: открытые заказы хранятся в `sell2` (`sold=0`), закрытые — в `sell`; категории меню — `type`, столы — `place`; тариф VIP означает `menu.price_vip`. Типовые задачи подключения любой кассы — ТЗ, приложение B.
