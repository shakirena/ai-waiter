# Feature #9: Вход гостя по QR-токену, визит, язык

*Stories: #75…#86 (таблица «User Stories»). Архитектура — `docs/arch/feature-9-guest-qr-entry.md` (ADR-9.1…9.7); при расхождении в технических деталях (пути и коды API, cookie, хранение сессии и языка, длина токена) приоритет у arch doc, в поведении для гостя и scope — у spec. Spec сверен с arch 2026-11-10, ответы пользователя на Q-2 и Q-3 внесены (2026-11-10).*

## Обзор

Гость сканирует QR-код на столе и попадает на `https://{домен}/t/{token}`. Сейчас это заглушка frontend (#6), токен никак не проверяется. Фича делает эту ссылку точкой входа гостя:

1. сервер по токену находит заведение и стол (ТЗ FR-1);
2. открывает визит стола или присоединяет гостя к уже открытому визиту — визит общий для всех устройств за столом, с одной корзиной (ТЗ 7, ADR-7.5);
3. выдаёт гостевую сессию (cookie), по которой следующие API гостя (#10 меню и корзина, #11 чат, #12 заказ) определяют `tenant_id` и визит, не принимая их от клиента (ТЗ NFR-4, CLAUDE.md «Мультиарендность»);
4. определяет язык гостя по браузеру и даёт сменить его в любой момент (ТЗ FR-2);
5. на недействительный токен отвечает понятной гостю ошибкой, которая ничего не говорит о других заведениях и столах.

Модель данных уже есть (#7): `tables.qr_token` (UNIQUE, `QR_TOKEN_PATTERN` — base64url 22–64 символа), `token_issued_at`, `is_active`; `visits` (`status` open/closed, `lang`, `closed_by`, `last_activity_at`, частичный уникальный индекс `uq_visits_open_table` — не больше одного открытого визита на стол). Схема БД не меняется, миграции нет: гостевая сессия — подписанная cookie без таблицы (arch ADR-9.2).

Заметка из анализа #60/#71 (arch `feature-60-demo-data-guard.md`, риск 1): проверка #71 переводит `/health/ready` в 503, но трафик не снимает. Поэтому при `APP_ENV=prod` вход по токенам столов демо-заведения `DEMO_TENANT_ID` отклоняется так же, как по неизвестному токену (FR-4, story #78).

## Роли

- **Гость** — анонимный посетитель с телефоном (ТЗ 2, NFR-5): сканирует QR, ничего не вводит, выбирает язык.
- **Администратор заведения** — косвенно: перевыпускает токен и отключает стол (UI — #27; в этой фиче только серверная функция перевыпуска).
- **Официант** — косвенно: закрывает визит (ТЗ FR-14a; endpoint — после авторизации персонала #19, в этой фиче только сервисная функция закрытия).
- **Злоумышленник** — подбирает токены, пользуется сфотографированным QR или демо-токенами из публичного репозитория (ТЗ 12, «Риски»).

## Допущения

- **D-1 (ТЗ 13, вопрос 8) — визит открывается первым сканированием QR.** На этапе 1 подтверждение официантом не требуется: первое успешное сканирование стола без открытого визита открывает визит, следующие присоединяются к нему. Пользователь подтвердил это для этапа 1 (2026-11-10). Нужен ли к пилоту режим «визит открывает официант» (ТЗ 12, митигация риска «заказ по сфотографированному QR»), решается в #19/#21 (Q-1, отложен); #9 этот вопрос не блокирует.
- **D-2 — один браузер, одна гостевая сессия.** Сканирование QR другого стола на том же телефоне заменяет сессию: гость переходит к новому столу.

## Решения пользователя (2026-11-10)

- **R-Q2 (бывший Q-2) — язык экрана ошибки по умолчанию — `az`.** Если заведение неизвестно (ошибка входа), а язык браузера не `az` и не `ru`, экран ошибки показывается на азербайджанском (FR-11, #85).
- **R-Q3 (бывший Q-3) — перевыпуск токена и отключение стола сразу обрывают сессии.** Действующие гостевые сессии стола перестают действовать на следующем же запросе после фиксации перевыпуска токена или `is_active = false`; гостям нужно отсканировать новый (или снова действующий) QR. Так перевыпуск закрывает доступ по сфотографированному QR (ТЗ 12). Реализация — arch ADR-9.2: в cookie хранится `tia` (`tables.token_issued_at` на момент выдачи), на каждом запросе `current_guest` сверяет его и `tables.is_active` с БД (FR-6, #80).

## Functional Requirements

- **FR-1 (ТЗ FR-1, ТЗ 7 `visits`) — вход по QR-токену открывает визит, #75.** `/t/{token}` остаётся маршрутом SPA (backend отдаёт `index.html`); страница гостя вызывает API входа `POST /api/guest/v1/entry` с телом `{"token": "...", "lang": "az" | "ru" | null}` (arch ADR-9.1). Сервер находит активный стол с таким `qr_token`, затем в одной транзакции:
  - если у стола нет открытого визита — создаёт визит `status = open`, `lang` — язык гостя (FR-7), `opened_at` и `last_activity_at` — текущее время;
  - выдаёт гостевую сессию (FR-6) и возвращает `200 GuestEntryResponse` (arch «API Contracts»): заведение (название, языки, язык по умолчанию, валюта), стол (название, тип `table`/`cabin`), визит (`id`, `opened_at`, `is_new`), текущий язык гостя.
  `tenant_id`, `table_id`, `hall_id`, `price_tier`, `qr_token` в ответе не возвращаются, `tenant_id` от клиента не принимается. Не `GET` — запрос создаёт визит, и превью ссылок в мессенджерах или prefetch браузера не должны открывать визиты. Токен в теле, а не в пути API — путь пишется в access-лог (NFR-3). Все ответы `/api/guest/v1/*` — с `Cache-Control: no-store`.
- **FR-2 (ТЗ 7, ADR-7.5) — второе устройство присоединяется к открытому визиту, #76.** Если у стола уже есть открытый визит, вход по токену не создаёт новый, а выдаёт сессию этого визита и обновляет `last_activity_at`. Одновременные входы с разных устройств к столу без визита дают ровно один открытый визит: вставка идёт через `INSERT … ON CONFLICT DO NOTHING` по `uq_visits_open_table`, пустой результат означает присоединение к визиту параллельного запроса (повторная выборка, до `OPEN_VISIT_ATTEMPTS = 3` попыток; затем 503 `try_again`, практически недостижимо) — arch ADR-9.3. Ответ содержит `visit.is_new = false`.
- **FR-3 (ТЗ FR-1, NFR-4) — единый ответ на недействительный токен, #77.** Токен недействителен, если:
  - не проходит `QR_TOKEN_PATTERN` (длина, символы) — в этом случае запрос к БД не выполняется (тело с токеном длиной вне 1…128 — стандартная 422 валидации тела);
  - стола с таким токеном нет: неизвестный токен или старый токен после перевыпуска;
  - стол принадлежит демо-заведению при `APP_ENV=prod` (FR-4).
  Во всех этих случаях ответ одинаковый: **404, тело `{"detail": {"code": "qr_invalid"}}`**, одни и те же заголовки (arch ADR-9.6). Визит не создаётся, cookie сессии не выставляется. В ответе нет названия заведения, стола, причины отказа и самого токена; по ответу нельзя отличить неизвестный, перевыпущенный и демо-токен.
  **Отключённый стол** (токен найден, `is_active = false`) — отдельный ответ **403 `{"detail": {"code": "table_inactive"}}`** без данных заведения и стола (arch ADR-9.6): у гостя в руках настоящий QR этого заведения, и «стол временно не обслуживается» понятнее, чем «неверный код». Визит не создаётся, cookie не выставляется.
  Frontend показывает понятный текст на AZ/RU (FR-11): на `qr_invalid` — «QR-код недействителен, обратитесь к официанту», на `table_inactive` — «Стол временно не обслуживается, обратитесь к официанту».
  **Защита от перебора (arch ADR-9.7).** Попытки входа ограничены по IP клиента через интерфейс `RateLimiter`: `GUEST_ENTRY_RATE_LIMIT` (по умолчанию 30 в минуту, `0` — выключено); превышение — 429 `rate_limited` с `Retry-After`. Ошибка самого `RateLimiter` (например, Redis недоступен в `scaled`) вход не блокирует (fail-open, WARNING в лог).
- **FR-4 (ТЗ NFR-4; arch #60 ADR-60.2, риск 1) — демо-токены в prod, #78.** При `APP_ENV=prod` вход по токену стола заведения `DEMO_TENANT_ID` отклоняется так же, как по неизвестному токену (FR-3). Действующая гостевая сессия визита демо-заведения в prod тоже недействительна — 401 `guest_session_invalid` (FR-6). Проверка — сравнение `tenant_id` с константой, без дополнительного запроса в БД; сервис получает флаг `reject_demo`, `app/guest` сам `Settings` не читает (arch ADR-9.6). При `APP_ENV=dev`/`test` демо-токены работают: на них построена разработка, сид печатает ссылки `/t/{token}`. `DEMO_TENANT_ID` берётся из `app.seed.data` и не дублируется. Новых переменных окружения и флага отключения проверки нет.
- **FR-5 (ТЗ FR-1, FR-15, NFR-4) — перевыпуск токена, #79.** Сервисная функция перевыпуска токена стола (вызывать её будет админка #27; в этой фиче — без endpoint и UI):
  - генерирует новый токен `secrets.token_urlsafe(24)` (`QR_TOKEN_BYTES = 24`: 192 бита, 32 символа base64url, проходит `QR_TOKEN_PATTERN`; arch ADR-9.5). Той же функцией генерации (`generate_qr_token`) создаются токены новых столов (коннектор `PUT /tables` #16, админка #27);
  - записывает его в `tables.qr_token`, `token_issued_at` = текущее время, с фильтром по `tenant_id`, в транзакции вызывающего; стола нет — `TableNotFoundError`;
  - старый токен после фиксации транзакции не работает: вход по нему — 404 `qr_invalid` (FR-3), а сессии, выданные до перевыпуска, — 401 `guest_session_invalid` (R-Q3, FR-6). Коллизия с существующим токеном (практически невозможна) приводит к повторной генерации внутри SAVEPOINT (до 3 раз), а не к ошибке 500.
  «Отзыв» токена в смысле ТЗ FR-1 и есть перевыпуск: история токенов не хранится. Временное отключение стола — `is_active = false` (#16/#27).
- **FR-6 (ТЗ NFR-4, ТЗ 7; CLAUDE.md «Мультиарендность») — гостевая сессия, #80.** Сессия — подписанная HMAC-SHA256 cookie без таблицы в БД (arch ADR-9.2). После успешного входа сервер выставляет cookie `aiw_guest`:
  - `HttpOnly`; `SameSite=Strict`; `Secure` — `GUEST_COOKIE_SECURE`, по умолчанию включён при `APP_ENV=prod` (ТЗ NFR-4: только HTTPS); `Path=/api/guest/`; `Max-Age` = `GUEST_SESSION_TTL_HOURS` × 3600 (по умолчанию 12 ч); без атрибута `Domain`;
  - значение `v1.<payload>.<sig>`: payload содержит только идентификаторы визита, заведения и стола, `tia` (`token_issued_at` стола на момент выдачи), язык и время выдачи — без QR-токена и персональных данных (ТЗ NFR-5). Подпись сверяется `hmac.compare_digest`; подделанное или изменённое значение отклоняется. Ключ — `GUEST_SESSION_SECRET` (≥ 32 символов), обязателен при `APP_ENV=prod` или `APP_MODE=scaled`; в `single` вне prod без него берётся случайный ключ процесса с WARNING;
  - сессия привязана к визиту. Все следующие запросы гостевого API (#10–#12) получают `tenant_id`, стол и визит только из сессии, через общую зависимость FastAPI `current_guest` (`GuestContext`). `GET /api/guest/v1/session` возвращает `GuestSessionResponse` — те же данные, что вход (FR-1), без `visit.is_new`, например после перезагрузки страницы;
  - проверка на каждом запросе (подпись, срок по `iat`, затем **один** запрос в БД по визиту, столу и заведению): сессия действительна, только пока визит открыт (FR-8), стол активен и его `token_issued_at` равен `tia` из cookie (R-Q3), а при `APP_ENV=prod` заведение не демо (FR-4). Ответы 401 (arch «API Contracts»):
    - `guest_session_required` — cookie нет, она повреждена, подпись неверна или истёк срок;
    - `guest_session_invalid` — токен стола перевыпущен, стол отключён, демо-заведение в prod, визит не найден по заведению, столу и визиту из cookie;
    - `visit_closed` — визит закрыт (FR-8).
  Ни один ответ не раскрывает данных чужого визита. Frontend при `guest_session_required`/`guest_session_invalid` сам повторяет вход по токену из URL, при `visit_closed` — только по кнопке гостя (FR-11).
- **FR-7 (ТЗ FR-2, AI-6) — язык гостя при входе, #82.** Порядок выбора (`resolve_entry_lang`, arch ADR-9.4):
  1. `lang` из тела запроса входа — явный выбор, который frontend хранит на устройстве (`localStorage`), если он есть в `tenants.languages`;
  2. язык из действующей cookie того же стола (повторный вход, перезагрузка);
  3. заголовок `Accept-Language`: по убыванию q-value первый тег, основной подтег которого (`az-AZ`, `az-Latn-AZ` → `az`; `ru-RU` → `ru`) есть в `tenants.languages`; `q=0` пропускается; разбор устойчив к мусору, заголовок длиннее 512 символов обрезается;
  4. язык заведения по умолчанию — первый элемент `tenants.languages` (заголовка нет, только `en`, `tr`, `*`, язык не поддерживается заведением).
  Блокирующего экрана выбора языка при первом входе нет: выбор — это видимый переключатель с уже предвыбранным языком (FR-11; отвечает на открытый вопрос 2 arch).
- **FR-8 (ТЗ FR-14a, ТЗ 7 `closed_by`) — закрытый визит, #81.** Сервисная функция закрытия визита: `status = closed`, `closed_at` — текущее время, `closed_by` из `VisitClosedBy` (`staff`/`pos`/`timeout`), `closed_by_staff_id` — для `staff`, если передан. Функция (`visits.close_visit`, arch ADR-9.3) работает в транзакции вызывающего, фильтрует визит по `tenant_id` и `status = open` и возвращает, закрыт ли визит этим вызовом. Повторное закрытие уже закрытого визита ничего не меняет (`closed_by` и `closed_at` не перезаписываются) и ошибкой не считается. Endpoint и событие EventBus о закрытии в #9 не появляются. Вызывать функцию будут: официант (#14/#21, после #19), касса по `order_status` (#17), автозакрытие по `visit_idle_close_hours` (#23). После закрытия:
  - гостевые сессии этого визита недействительны (FR-6, ответ 401 `visit_closed`);
  - следующее сканирование QR стола открывает новый визит (FR-1), с новой пустой корзиной и новым диалогом; старый визит со строками корзины, сообщениями и заказами остаётся в истории.
- **FR-9 (ТЗ FR-2) — смена языка в любой момент, #83.** Гость с действительной сессией меняет язык: `PUT /api/guest/v1/session/lang` с телом `{"lang": "az"}` (только `application/json`). Допустимы только значения из `Lang`, которые есть в `tenants.languages` заведения; язык вне списка заведения — 422 `lang_not_supported`, значение не из `Lang` — 422 валидации тела; язык не меняется. Успех — 200 `GuestSessionResponse` и новая `Set-Cookie` с переподписанным языком; в той же транзакции обновляются `visits.lang` и `visits.last_activity_at`. Без действительной сессии — 401 (FR-6).
- **FR-10 (ТЗ 7 `visits.lang`) — где хранится язык (arch ADR-9.4).** Язык интерфейса — у каждого устройства, в payload cookie сессии: за одним столом могут сидеть гости с разными языками, и смена языка одним из них не переключает экран другого. `visits.lang` (NOT NULL) — язык устройства, открывшего визит, затем последний явный выбор любого гостя визита (FR-9). Его читает сервер там, где контекста устройства нет: панель официанта, фоновые задачи. Чат #11 берёт язык из `current_guest.lang`, ответ бота — по правилу AI-6 «язык последнего сообщения».
- **FR-11 (ТЗ FR-1, FR-2, NFR-2) — минимальный экран гостя, #84–#86.** Заглушка `GuestPage` (`/t/:token`) заменяется минимальным экраном:
  - при открытии вызывает `POST /api/guest/v1/entry` (передаёт сохранённый на устройстве язык, если есть) и показывает название заведения, название стола и переключатель языка — #84;
  - на ошибки показывает экран без кода ошибки, токена и технических подробностей — #85: `qr_invalid` — «QR-код недействителен, обратитесь к официанту»; `table_inactive` — «Стол временно не обслуживается, обратитесь к официанту»; `rate_limited` — «Слишком много попыток, повторите через минуту»; `visit_closed` (на последующих запросах) — «Визит завершён» с кнопкой «Начать заново» (новый вход только по кнопке); сетевая ошибка или 5xx — «Сервис временно недоступен» с кнопкой «Повторить». Язык экрана ошибки — язык браузера (`navigator.language`: `az`/`ru`), иначе `az` (R-Q2);
  - переключатель AZ/RU показывает только языки заведения (при одном языке не показывается), вызывает FR-9, сохраняет выбор на устройстве (`localStorage` с try/catch) и сразу меняет тексты экрана без перезагрузки — #86;
  - `frontend/index.html` получает `<meta name="referrer" content="same-origin">`: путь `/t/{token}` не уходит внешним ресурсам через `Referer` (arch «Security»).
  Полный интерфейс гостя (меню, корзина, чат, заказ) — #13. Тексты на азербайджанском до запуска проверяет носитель языка (ТЗ AI-6, примечание сида #53).
- **FR-12 (ТЗ 7 `visits.last_activity_at`) — активность визита, #76, #83.** В #9 `last_activity_at` обновляется при входе (создание и присоединение) и при смене языка; `GET /session` его не обновляет. Гостевые действия #10–#12 обновляют его функцией `visits.touch_visit` (нужно автозакрытию #23).

## Non-Functional Requirements

- **NFR-1 (ТЗ NFR-4, FR-1) — непредсказуемость токенов.** Токены генерируются только через `secrets` (не `random`, не UUIDv1/v7, не хеш от идентификатора стола), не меньше 128 бит энтропии. Сравнение токена выполняет БД по уникальному индексу `tables.qr_token`. Демо-токены `dev_token(n)` детерминированы и допустимы только вне prod (FR-4).
- **NFR-2 (ТЗ NFR-4, CLAUDE.md «Мультиарендность») — tenant-изоляция.** `tenant_id` гостя определяется только сервером: при входе — по найденному столу, дальше — по сессии. Гостевой API не принимает `tenant_id`, `table_id` и `visit_id` из запроса как источник прав. Все запросы к `visits` и `tables` после входа фильтруются по `tenant_id` сессии. Ответы об ошибках одинаковы для «чужого» и «несуществующего» (FR-3, FR-6); отключённый стол отвечает отдельным кодом `table_inactive`, но без данных заведения и стола (ADR-9.6). Межарендные ссылки исключены и на уровне БД (составные FK, DEC-006).
- **NFR-3 (ТЗ NFR-4, NFR-6) — без секретов в логах.** QR-токен, значение cookie сессии и секрет подписи не пишутся в логи приложения, тексты ошибок и ответы API (кроме самой `Set-Cookie`). Структурированный лог входа содержит `tenant_id`, `table_id`, `visit_id`, признак «визит создан / присоединение» и язык. Отказ входа логируется на уровне INFO без токена, cookie и `Accept-Language` целиком — только машинный код и `tenant_id`/`table_id`, если известны (arch «Security»); объём отказных записей ограничен rate-limit входа (NFR-4). Путь `/t/{token}` в access-логе uvicorn/Caddy остаётся (arch, риск R-2; фильтр — #32).
- **NFR-4 (ТЗ NFR-4, AI-7; ТЗ 12) — защита от перебора (arch ADR-9.7).** При 192 битах энтропии перебор токенов невозможен, а вход по одному столу не размножает визиты (FR-2). Чтобы endpoint входа не был дешёвым способом нагрузить БД, в #9 вводится лимит попыток входа по IP: `RateLimiter.hit(rate_key("guest_entry", "ip", client_ip_key(host)), limit=GUEST_ENTRY_RATE_LIMIT, window=60)`; IP — `request.client.host` (за доверенным прокси, DEC-005), IPv6 сводится к префиксу /64; превышение — 429 `rate_limited` с `Retry-After`; сбой лимитера — fail-open. Только через интерфейс `RateLimiter`, без прямого обращения к Redis (CLAUDE.md). Лимиты по столу и гостевых действий (#10–#12, сообщения ИИ) — #26/#22.
- **NFR-5 (ТЗ NFR-4) — CSRF и cookie.** Запросы, меняющие состояние (вход, смена языка), принимают только JSON-тело (Pydantic-модель): `text/plain` и form дают 422. Вместе с `SameSite=Strict` это не даёт стороннему сайту выполнить их от имени гостя. CORS для гостевого API не открывается. Service Worker не перехватывает `/api` (`navigateFallbackDenylist`).
- **NFR-6 (ТЗ NFR-2, NFR-1) — производительность.** Вход — один поиск стола по уникальному индексу и одна транзакция с визитом; без вызовов ИИ и внешних сервисов. Проверка сессии на запросах #10–#12 — не больше одного-двух запросов по первичным ключам или индексам. Ориентир: p95 входа ≤ 200 мс на сервере без нагрузки (без учёта сети).
- **NFR-7 (ТЗ NFR-8, 9.2) — переносимость.** Одинаково в `single` и `scaled`, на Windows и Linux. Состояние сессии не хранится в памяти процесса (в `scaled` несколько экземпляров `api`). Конфигурация — только env: `GUEST_SESSION_SECRET` (обязателен при `APP_ENV=prod` или `APP_MODE=scaled`, общий для всех экземпляров `api`), `GUEST_SESSION_TTL_HOURS` (12, 1…72), `GUEST_COOKIE_SECURE` (по умолчанию — `true` при prod), `GUEST_ENTRY_RATE_LIMIT` (30, `0` — выкл.); в `.env.example` без значения секрета, команда генерации секрета — в README.
- **NFR-8 (ТЗ NFR-5) — персональные данные.** Сессия анонимна: в ней и в визите нет IP, User-Agent и других данных о личности. Язык — не персональные данные.
- **NFR-9 — тестируемость.** Unit-тесты (без БД, `-m "not db and not scaled"`) — разбор `Accept-Language`, генерация токена, кодек cookie (подпись, подмена, TTL, версия), формат ответов и коды ошибок, флаги cookie, 429 и fail-open лимитера, prod/dev-ветви FR-4. db-тесты (маркер `db`) — вход, присоединение, гонка двух входов (FR-2), перевыпуск, закрытие визита, изоляция заведений. Frontend — Vitest для экранов #84–#86.

## Acceptance Criteria

Один сценарий на story (SD-1). Граничные случаи — в таблице ниже.

### AC-1 (#75) — вход открывает визит
**Given** активный стол заведения с действительным QR-токеном, у стола нет открытого визита
**When** гость открывает ссылку `/t/{token}`, и frontend вызывает `POST /api/guest/v1/entry` с этим токеном
**Then** создаётся открытый визит стола, ответ 200 содержит название заведения, название стола, визит с `is_new = true` и язык гостя, а в ответе выставлена cookie `aiw_guest` с `HttpOnly`

### AC-2 (#76) — присоединение к открытому визиту
**Given** у стола уже есть открытый визит, начатый с другого устройства
**When** второй гость входит по QR-токену того же стола
**Then** новый визит не создаётся: гость получает сессию существующего визита (`is_new = false`), и у стола остаётся ровно один открытый визит

### AC-3 (#77) — единый ответ на недействительный токен
**Given** токен неизвестен, не проходит `QR_TOKEN_PATTERN` или отозван перевыпуском
**When** гость вызывает API входа с этим токеном
**Then** ответ во всех случаях один и тот же — 404 `{"detail": {"code": "qr_invalid"}}` с одинаковыми заголовками, без названия заведения, стола и причины; визит не создаётся, cookie не выставляется

### AC-4 (#78) — демо-токены в prod
**Given** приложение запущено с `APP_ENV=prod`, в базе есть активный стол заведения `DEMO_TENANT_ID`
**When** гость вызывает API входа с токеном этого стола
**Then** ответ совпадает с ответом на неизвестный токен (404 `qr_invalid`, AC-3), визит не создаётся

### AC-5 (#79) — перевыпуск токена
**Given** у активного стола действует токен T1
**When** вызывается сервисная функция перевыпуска токена и транзакция фиксируется
**Then** у стола новый токен T2 (32 символа base64url, 192 бита, `QR_TOKEN_PATTERN`) и новое `token_issued_at`; вход по T1 даёт ответ AC-3, вход по T2 — успешен

### AC-6 (#80) — визит определяется по сессии
**Given** гость вошёл по QR и получил cookie сессии открытого визита
**When** он запрашивает `GET /api/guest/v1/session`
**Then** сервер возвращает заведение, стол, визит и язык из сессии, не принимая `tenant_id`/`visit_id` из запроса; без cookie или с подделанной cookie — 401 `guest_session_required`

### AC-7 (#81) — сессия закрытого визита недействительна
**Given** у гостя есть cookie сессии визита, который закрыт сервисной функцией закрытия визита
**When** гость обращается к гостевому API с этой cookie
**Then** ответ — 401 `visit_closed`, без данных визита

### AC-8 (#82) — язык из браузера
**Given** заведение поддерживает `az` и `ru`, браузер гостя присылает `Accept-Language: ru-RU,ru;q=0.9,en;q=0.8`
**When** гость впервые входит по QR-токену
**Then** язык сессии в ответе — `ru`; для браузера без `az`/`ru` в `Accept-Language` — язык заведения по умолчанию (первый в `tenants.languages`)

### AC-9 (#83) — смена языка
**Given** гость с действительной сессией, язык сессии `ru`, заведение поддерживает `az`
**When** гость отправляет `PUT /api/guest/v1/session/lang` с `{"lang": "az"}`
**Then** ответ 200 подтверждает `az` и переподписывает cookie, и следующий `GET /api/guest/v1/session` возвращает `az`

### AC-10 (#84) — экран стола
**Given** действительная QR-ссылка активного стола
**When** гость открывает `/t/{token}` в браузере телефона
**Then** экран показывает название заведения, название стола и переключатель языка вместо заглушки

### AC-11 (#85) — экран ошибки
**Given** QR-ссылка с недействительным токеном
**When** гость открывает её в браузере
**Then** экран показывает на языке браузера (AZ/RU, иначе AZ) понятное сообщение «QR-код недействителен, обратитесь к официанту» без кода ошибки, токена и технических подробностей

### AC-12 (#86) — переключатель языка
**Given** гость на экране стола, заведение поддерживает AZ и RU
**When** гость нажимает переключатель на другой язык
**Then** тексты экрана сразу меняются на выбранный язык без перезагрузки страницы, выбор сохраняется на сервере (AC-9) и на устройстве и остаётся после перезагрузки

## Вне scope

- **Endpoint-ы персонала** для открытия и закрытия визита (ТЗ FR-14a): нужна авторизация персонала (#19), UI — панель официанта (#14, #21). В этой фиче — только сервисная функция закрытия (FR-8) и правило «закрытый визит → следующее сканирование открывает новый».
- **Режим «визит открывает официант»** (подтверждение визита до первого заказа) — решается в #19/#21 (Q-1, отложен).
- **Автозакрытие визита по `visit_idle_close_hours`** (#23) и **закрытие по сигналу кассы** `order_status` (#17) — вызывают функцию FR-8.
- **UI отзыва и перевыпуска токена, печать QR в PDF, создание столов** — админка #27; приём столов от коннектора — #16.
- **Rate-limit по столу и гостевых действий** (меню, корзина, сообщения ИИ) — #26/#22. Лимит попыток входа по IP входит в #9 (NFR-4, #77).
- **Ротация `GUEST_SESSION_SECRET` двумя ключами** без разлогинивания гостей — не на этапе 1 (arch, открытый вопрос 3).
- **История отозванных токенов** и отдельный ответ «QR-код устарел» — нет (arch, открытый вопрос 4): перевыпущенный токен отвечает как неизвестный.
- **Таблица гостевых сессий** и точечный отзыв одного устройства — нет (arch ADR-9.2).
- **Полный интерфейс гостя** (меню, корзина, чат, статус заказа, PWA-офлайн) и полноценная i18n — #13. API меню и корзины — #10, чат — #11, заказ — #12.
- **Язык ответа бота** (AI-6) — #11.
- **Удаление демо-заведения из боевой базы** и `/health/ready` — #60/#71 (влиты).
- **Геопривязка или проверка «гость в заведении»** (ТЗ 12, риск сфотографированного QR) — митигация через подтверждение официантом и перевыпуск токенов.

- **Q-1 (ТЗ 13, вопрос 8) — отложен до #19/#21.** Для этапа 1 визит открывается первым сканированием QR (D-1, подтверждено 2026-11-10). Нужен ли к пилоту (этап 2) режим «визит открывает официант» (например, настройка заведения), решается при анализе #19/#21; #9 не блокирует.
- **Q-4 — отключение стола без перевыпуска (E-20).** Сессия stateless, поэтому после повторного включения стола прежние cookie снова действуют. Если отключение должно обрывать сессии навсегда, admin #27 при отключении может перевыпускать токен; решается при анализе #27, #9 не блокирует.

Закрытые:

- **Q-2** — принято `az` (R-Q2, 2026-11-10).
- **Q-3** — принято: перевыпуск и отключение сразу обрывают сессии (R-Q3, 2026-11-10).
- **A-1…A-5** (вопросы к architect) — решены в arch: пути и коды API — ADR-9.1, ADR-9.6, «API Contracts» (FR-1, FR-3, FR-6, FR-9); хранение и атрибуты cookie, привязка к `token_issued_at` — ADR-9.2 (FR-6); язык — ADR-9.4 (FR-10); `last_activity_at` — FR-12; логирование отказов — arch «Security» (NFR-3).
