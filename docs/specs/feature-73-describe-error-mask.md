# Feature #73: Маскирование DATABASE_URL в describe_error

*Story: #73 (type:bug, сам issue и есть story; дочерних issue нет). Архитектура — `docs/arch/feature-73-describe-error-mask.md`; при расхождении приоритет у arch doc.*

## Обзор

`Database.describe_error` (`backend/app/db/session.py`) собирает текст ошибки по цепочке `__cause__`/`__context__` и через `_mask` заменяет на `***` только пароль из `DATABASE_URL`, в том числе в URL-кодированном виде. Хост, порт, имя пользователя и имя базы остаются в тексте как есть. В текстах ошибок драйвера они встречаются часто, например `connection to server at "192.0.2.10", port 5432 failed`, `Connect call failed ('192.0.2.10', 5432)` или `password authentication failed for user "waiter"`.

Текст `describe_error` выводится:
- в WARNING `Database.ping` и `_check` компонента `database` (`app/api/health.py`, `/health/ready`);
- в WARNING `DEMO_CHECK_FAILED` проверки демо-данных (`app/api/demo_data.py`, #71);
- в stderr сида `python -m app.seed` (код 1);
- в отчёт синхронизации меню `python -m app.menu_sync` (`safe_text(database.describe_error(exc), MAX_SHOWN_ERROR_CHARS)`).

Репозиторий публичный, и логи с выводом консоли прикладывают к issue. Адреса серверов туда попадать не должны (CLAUDE.md, раздел «Документация»). Ограничение существует с #7 и записано как известное в NFR-1 spec #60 и в arch #60, раздел Security (security review #60, LOW).

Исправление: маскировать в тексте все значения из `DATABASE_URL`, кроме схемы и драйвера. Тип исключения и остальной текст сообщения сохраняются, чтобы причина сбоя оставалась понятной.

## Роли

- **Администратор платформы / оператор** — читает логи службы (`single`) или контейнера (`scaled`), stderr сида и отчёт синхронизации меню. Ему нужна причина сбоя (таймаут, отказ в соединении, неверный пароль, нет базы), но не адрес сервера.
- **Разработчик / пользователь репозитория** — прикладывает логи к публичным issue.

## Functional Requirements

- **FR-1 (ТЗ NFR-4) — что маскируется.** В тексте, который возвращает `describe_error`, каждое вхождение следующих значений из `DATABASE_URL` заменяется на `***`:
  - хост (имя домена, IPv4, IPv6; для IPv6 — и в квадратных скобках, и без них);
  - порт, если он явно указан в URL;
  - имя пользователя;
  - имя базы;
  - пароль (как сейчас);
  - значения хоста и порта из query-параметров (`?host=…`, `?port=…`), если они заданы так, включая списки через запятую.
  Каждое значение маскируется и в исходном виде, и в URL-кодированном (`quote(..., safe="")`, `quote_plus`), как сейчас пароль.
- **FR-2 — что сохраняется.** Имя типа каждого исключения в цепочке, разделитель ` <- ` и весь остальной текст сообщений не меняются. Схема и драйвер (`postgresql+asyncpg`) не секретны и не маскируются. Маскирование не должно портить имена типов исключений и обычные слова, если короткое значение (например, пользователь `u` или база `x`) встречается внутри них. Как именно выделяются вхождения (границы токенов, кавычки, порядок замен), решает architect.
- **FR-3 — URL без пароля.** Если пароля в `DATABASE_URL` нет, хост, порт, пользователь и база всё равно маскируются. Сейчас `_mask` в этом случае возвращает текст без изменений — это часть бага.
- **FR-4 — неразбираемый URL.** Если `make_url(DATABASE_URL)` бросает исключение (например, нечисловой порт), `describe_error` по-прежнему возвращает `UNPARSABLE_URL_TEXT` и не показывает исходный текст. Константа и её текст не меняются.
- **FR-5 — контракт вызывающих не меняется.** Сигнатура `describe_error(exc) -> str`, обход цепочки причин (по одному разу, без зацикливания) и места вызова (`health.py`, `demo_data.py`, `seed/__main__.py`, `menu_sync/__main__.py`) остаются прежними. Меняется только результат маскирования.

## Non-Functional Requirements

- **NFR-1 (ТЗ NFR-4; spec #60 NFR-1) — без деталей подключения в выводе.** Ни одно значение из `DATABASE_URL`, кроме схемы и драйвера, не попадает в текст `describe_error`, а значит и в лог, stderr сида и отчёт синхронизации меню. Это снимает «известное ограничение» из NFR-1 spec #60. ТЗ NFR-4 требует хранить секреты в переменных окружения, а не в коде. Адреса серверов, пользователь и база — часть того же секрета `DATABASE_URL`. В ТЗ нет отдельного пункта о секретах в логах, ближайший — NFR-4; формат логов задаёт NFR-6.
- **NFR-2 — переносимость (ТЗ NFR-8).** Поведение одинаково в режимах `single` и `scaled`, на Windows и Linux; маскирование не зависит от ОС и драйвера.
- **NFR-3 — тестируемость.** Unit-тесты без БД (как в `backend/tests/test_db_session.py`) запускаются в матрице CI на Windows и Linux, без маркеров `db` и `scaled`. Адреса в тестах и примерах — только из документационных диапазонов (`192.0.2.0/24`, `2001:db8::/32`, `*.example.com`, `*.invalid`).
- **NFR-4 — стоимость.** Разбор URL и замены выполняются только при формировании текста ошибки; на успешный путь (`ping`, сессии) не влияют.

## User Story

As a администратор платформы, I want to видеть в логах и выводе консоли причину ошибки БД без адреса сервера, порта, пользователя и имени базы so that логи можно прикладывать к публичным issue, не раскрывая инфраструктуру.

## Acceptance Criteria

### AC-1 (#73) — значения из DATABASE_URL заменены на `***`

**Given** `DATABASE_URL` равен `postgresql+asyncpg://waiter_user:pw-s3cret@192.0.2.10:5433/waiter_db`, а текст ошибки драйвера содержит хост, порт, пользователя, базу и пароль (например, `OSError: connection to server at "192.0.2.10", port 5433 failed: password pw-s3cret rejected for user "waiter_user" database "waiter_db"`)
**When** вызывается `Database.describe_error` для этого исключения
**Then** возвращается `OSError: connection to server at "***", port *** failed: password *** rejected for user "***" database "***"`: имя типа и остальной текст сохранены, ни одно из пяти значений в тексте не встречается

Остальные сценарии — граничные случаи ниже; они проверяются тем же способом (вызов `describe_error` с подставленным `DATABASE_URL`).

## Граничные случаи

| # | Ситуация | Ожидаемое поведение |
|---|----------|---------------------|
| E-1 | Порт в URL не указан (`…@db.example.com/waiter_db`), драйвер печатает порт по умолчанию `5432` | `5432` не маскируется: это общеизвестное значение по умолчанию, а не значение из `DATABASE_URL`. Хост, пользователь и база маскируются. Если architect решит маскировать и порт по умолчанию, это допустимо (лишнее маскирование не нарушает NFR-1) |
| E-2 | Пользователь и база совпадают (`waiter:…@…/waiter`) | Все вхождения заменены на `***`, результат не зависит от порядка замен |
| E-3 | Одно значение — подстрока другого (пользователь `waiter`, база `waiter_db`; хост `db.example.com`, база `db`) | Сначала маскируется более длинное значение; в тексте не остаётся хвостов вроде `***_db` из одного и `db` из другого |
| E-4 | Короткое значение встречается внутри обычных слов (пользователь `u`, база `x`; база `waiter` внутри `ai-waiter` — `application_name` из `SERVER_SETTINGS`) | Имена типов исключений не портятся (`RuntimeError` остаётся `RuntimeError`, не `R***ntimeError`). Внутри слова (буквы, цифры, `_` с обеих сторон) значение не маскируется. Отдельный токен маскируется, в том числе в составе через дефис или точку (`ai-waiter` → `ai-***` допустимо). Точное правило границ — за architect |
| E-5 | Хост — домен (`db.example.com`) | Маскируется целиком; точки внутри значения границами не считаются. Нужно ли сравнивать без учёта регистра — решает architect |
| E-6 | Хост — IPv6 в скобках (`…@[2001:db8::1]:5432/…`) | Маскируются и `[2001:db8::1]`, и `2001:db8::1` (драйвер печатает адрес без скобок); скобки, если остаются, вокруг `***` допустимы |
| E-7 | Хост задан в query-параметре (`postgresql+asyncpg://waiter@/waiter_db?host=db.example.com&port=5433` или список `?host=192.0.2.10,192.0.2.11`) | Каждое значение `host` и `port` из query маскируется так же, как хост и порт из основной части URL |
| E-8 | URL без пароля (`postgresql+asyncpg://waiter@db.example.com/waiter_db`) | Хост, пользователь и база маскируются (FR-3); сообщения без значений возвращаются без изменений |
| E-9 | Пользователь, пароль или база в URL-кодированном виде (`p%40ss%2Fword`, пользователь `svc%2Bwaiter`) | Маскируются и декодированное значение (`p@ss/word`, `svc+waiter`), и закодированное (как сейчас для пароля, тест `test_describe_error_masks_url_encoded_password`) |
| E-10 | В тексте исключения вся строка подключения | Остаётся только схема с драйвером: `postgresql+asyncpg://***:***@***:***/***` |
| E-11 | URL не разбирается (`…@db.invalid:port/x`) | `UNPARSABLE_URL_TEXT`, как сейчас (FR-4, тест `test_describe_error_with_unparsable_url_hides_text`) |
| E-12 | Пустое сообщение исключения, цепочка с циклом | Как сейчас: только имя типа, цикл обходится один раз (тесты `test_describe_error_without_password_and_empty_message`, `test_describe_error_follows_implicit_context_once` должны проходить без изменения ожиданий) |
| E-13 | URL с доменом, драйвер печатает разрешённый IP (`connection to server at "db.example.com" (192.0.2.10)`) | **Открытый вопрос, по умолчанию вне scope.** IP нет в `DATABASE_URL`, по значению его не замаскировать. Маскировать ли все IPv4/IPv6-литералы по шаблону, решает architect (ADR в arch #73). Если нет, это остаётся известным ограничением и записывается в arch #73, раздел Security |

## Вне scope

- Маскирование других секретов: `REDIS_URL` (для Redis в `_check` уже выводятся только имена классов исключений, `_exception_names`, #71), ключей коннекторов, API-ключа модели.
- Маскирование IP, который драйвер получил DNS-разрешением домена (E-13), — если architect не решит иначе.
- Изменение мест вызова `describe_error`, формата логов, `exc_info` (traceback уже не пишется, #71).
- Изменение текста `UNPARSABLE_URL_TEXT`.
- Деплой: G6 для этой задачи не планируется (код библиотечный, без миграций и конфигурации).

## Technical Notes

- Слои: только backend, `app/db/session.py` (`Database.describe_error`, `Database._mask`; возможно, вспомогательная функция сбора значений из `make_url(...)`: `host`, `port`, `username`, `password`, `database`, `query["host"]`, `query["port"]`). API, модели, миграции и frontend не затрагиваются.
- Вызывающие (без изменения кода, только docstring/комментарии «пароль → `***`» → «детали подключения → `***`»): `app/api/health.py` (модульный docstring, `_check`), `app/api/demo_data.py`, `app/seed/__main__.py`, `app/menu_sync/__main__.py` (модульный docstring), docstring `Database.ping` и `describe_error`.
- В `app/menu_sync/__main__.py` текст обрезается `safe_text(..., MAX_SHOWN_ERROR_CHARS)` после маскирования; порядок верный, менять не нужно.
- Существующие тесты `backend/tests/test_db_session.py` используют URL с пользователем `u` и базой `x` (`postgresql+asyncpg://u:…@db.invalid/x`) и ждут точный текст (`"RuntimeError: raw ***, quoted ***"`, `"TimeoutError"`). Их ожидания должны остаться верными — это и есть проверка E-4. Если architect решит, что хост `db.invalid` в этих текстах встречаться не должен, ожидания можно не менять: в сообщениях тестов хоста нет.
- Новые unit-тесты (без маркеров `db`/`scaled`): AC-1, E-1…E-10, E-13 (если решено маскировать IP — проверка шаблона, иначе тест не нужен). Тест `test_ping_failure_returns_false_and_masks_password` расширить проверкой отсутствия хоста в WARNING.
- ТЗ: NFR-4, NFR-6, NFR-8. CLAUDE.md, раздел «Документация» (публичный репозиторий).

## Открытые вопросы

1. **E-13 — разрешённый IP в тексте драйвера.** Маскировать ли по шаблону все IPv4/IPv6-литералы, а не только значения из URL? Плюс: закрывает и этот путь утечки. Минус: лишнее маскирование чисел вида `1.2.3.4` в версиях и сообщениях. Решение — за architect.
2. **Правило границ для коротких значений (E-4).** Предложение: значение маскируется, если рядом с ним нет символов `[A-Za-z0-9_]`; внутри слова — нет. Остаточный риск: пользователь `waiter` в тексте `waiterdb` не замаскируется. Решение и оценка риска — за architect.
3. **Регистр хоста (E-5).** Драйвер может напечатать домен в другом регистре. Сравнивать без учёта регистра или нет — решает architect.
4. **Порт по умолчанию (E-1).** По умолчанию не маскируется, лишнее маскирование допустимо.
