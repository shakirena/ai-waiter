# ТЗ: ИИ-официант (пилот с заделом под SaaS)

Версия 0.4 — черновик для обсуждения

**Изменения относительно v0.2 (версии 0.3–0.4):**
- ИИ-официант — самостоятельный продукт, не зависящий от кассы. Связь с кассами идёт через собственный Integration API и коннекторы (раздел 4).
- Стек зафиксирован: Python + FastAPI (раздел 8).
- Хостинг: пробный запуск нативно на сервере заведения (Windows Server 2019, без Docker, Cloudflare Tunnel), затем перенос на VPS без изменения кода (раздел 9). Backend работает в двух режимах: `single` и `scaled` (раздел 8).
- В кассе одно заведение; `type` — категории меню, `place` — столы.
- Модель данных переписана под PostgreSQL, с `tenant_id` и сущностью «визит» (раздел 7).
- Приложение A: программа «restoran» (Yii2) теперь первый коннектор. Её таблицы для хранения данных ИИ-официанта не используются.
- Учтены замечания разбора: признак «аллергены проверены», тариф стола, отзыв QR-токенов, расширенные статусы заказа, все числовые пороги вынесены в настройки.

## 1. Цель и рамки

Веб-приложение, которое открывается у гостя по QR-коду на столе (или в кабинете). ИИ-официант общается на азербайджанском и русском, показывает меню, помогает собрать заказ, отвечает на вопросы о составе блюд, вызывает живого официанта и просит оценку.

**Независимость от кассы.** У ИИ-официанта своя база, своя панель официанта и своя админка. Касса подключается через коннектор и служит источником меню и цен и получателем подтверждённых заказов. Без коннектора система тоже работает: меню загружается из файла, официант переносит заказ в кассу вручную. Цены и позиции берутся из кассы (или из файла импорта), второй источник цен вручную не ведётся.

Пилот: одно заведение, касса — собственная Yii2-программа «restoran». Архитектура сразу многоарендная (multi-tenant): другие заведения и кассы (r_keeper, iiko, Poster, Jowi и т.д.) подключаются новым коннектором без изменения ядра.

Вне рамок пилота: онлайн-оплата, доставка, лояльность, голосовой ввод, приложение в сторах.

## 2. Роли

1. Гость — сканирует QR, общается с ботом, оформляет заказ, вызывает официанта, оставляет оценку.
2. Официант — видит на своём устройстве заказы и вызовы по столам, подтверждает или отклоняет их.
3. Администратор заведения — управляет столами и QR, описаниями блюд, аллергенами, стоп-листом, смотрит отзывы.
4. Владелец платформы — заводит заведения, выпускает ключи коннекторов, следит за синхронизацией.
5. Коннектор (техническая роль) — программа на стороне кассы, которая обменивается данными через Integration API по своему ключу.

## 3. Функциональные требования

Все числовые пороги (N секунд, N минут, лимиты) хранятся в настройках заведения со значениями по умолчанию из раздела 3.4.

### 3.1 Гость (чат)

- FR-1. Вход по QR: ссылка вида `https://{домен}/t/{token}`. Токен — случайная непредсказуемая строка (не менее 128 бит), по которой сервер находит заведение и стол. Гость ничего не вводит. Токен можно отозвать и перевыпустить (новый QR), старый после этого не работает.
- FR-2. Выбор языка (AZ/RU) при первом входе, определение по языку браузера, смена в любой момент. Бот отвечает на языке гостя.
- FR-3. Меню: категории, карточки блюд (фото, описание, вес, цена, теги). Доступно и без чата, обычным списком. Цена показывается по тарифу стола (см. FR-15).
- FR-4. Диалог с ИИ: рекомендации («что-то без мяса до 20 манат»), ответы о составе, аллергенах, остроте, порциях, времени приготовления.
- FR-5. Корзина: добавить, убрать, изменить количество, комментарий к позиции («без лука»). ИИ меняет корзину только через функции системы, корзина всегда видна на экране отдельно от чата.
- FR-6. Оформление: гость видит итог (позиции, цены, сумма) и явно нажимает «Отправить официанту». Заказ уходит только по кнопке, не по фразе в чате.
- FR-7. Дозаказ: добавление позиций в рамках того же визита. Каждый дозаказ — отдельный заказ в визите, со своим подтверждением.
- FR-8. Вызов официанта: кнопка и фраза в чате. Причины: позвать, счёт, помощь. Защита от спама: не чаще раза в `call_cooldown_sec`.
- FR-9. Статус заказа виден гостю: «отправлен», «принят официантом», «изменён официантом» (с перечнем изменений), «отклонён» (с причиной).
- FR-10. Оценка: после закрытия визита или по кнопке. 1–5 звёзд, комментарий. Оценка не выше `low_rating_threshold` сразу уведомляет администратора.

### 3.2 Панель официанта

- FR-11. Живая лента событий (новые заказы, вызовы) по столам со звуком и вибрацией, через WebSocket. Резервный канал — Telegram.
- FR-12. Действия: принять, отклонить с причиной, отметить «вызов обработан». Если заказ не подтверждён за `order_escalation_min`, он получает статус `escalated`, и администратор получает уведомление в панели и в Telegram.
- FR-13. Официант может править заказ перед подтверждением: убрать позицию, изменить количество. Гость видит изменения (FR-9), итог пересчитывается.
- FR-14. Работает как PWA на телефоне, вход по PIN или логину.
- FR-14a. Официант открывает и закрывает визит стола. Если касса сообщает о закрытии счёта (возможность `order_status`), визит закрывается автоматически.

### 3.3 Админка

- FR-15. Столы и кабинеты: создание, название, тариф цен (`default`, `vip` и т.д.), связь со столом кассы (`external_id`), генерация QR (PDF для печати), отзыв и перевыпуск токена.
- FR-16. Меню: название, цена и наличие приходят из кассы и в админке не редактируются. Админ дополняет только то, чего нет в кассе: названия и описания на AZ/RU, фото, состав, аллергены, теги, острота, время приготовления.
- FR-16a. Аллергены выбираются из справочника (по умолчанию 14 аллергенов по стандарту ЕС). У блюда есть флаг «аллергены проверены». Без флага ИИ считает данные неизвестными (AI-2), даже если список пуст.
- FR-17. Стоп-лист: берётся из кассы, если коннектор это умеет; иначе ручной переключатель в админке.
- FR-18. Отзывы и диалоги: просмотр, фильтр по оценке, экспорт.
- FR-19. Правила поведения бота: приветствие, тон, что рекомендовать в первую очередь (акции, блюдо дня).
- FR-20. Состояние интеграции: время последней синхронизации меню, ошибки коннектора, заказы, не принятые кассой, кнопка «синхронизировать сейчас».
- FR-21. Настройки заведения: пороги из раздела 3.4, языки, валюта, часовой пояс.

### 3.4 Значения порогов по умолчанию

| Параметр | По умолчанию |
|---|---|
| `call_cooldown_sec` — интервал между вызовами официанта со стола | 60 |
| `order_escalation_min` — время до эскалации неподтверждённого заказа | 5 |
| `low_rating_threshold` — оценка, после которой уведомляется админ | 2 |
| `msg_max_chars` — длина сообщения гостя | 500 |
| `msg_per_visit` — сообщений ИИ за визит | 60 |
| `msg_per_table_hour` — сообщений ИИ со стола в час | 120 |
| `visit_idle_close_hours` — автозакрытие забытого визита | 6 |
| `dialog_retention_days` — хранение диалогов | 90 |
| `menu_stale_alert_min` — алерт, если меню давно не синхронизировалось | 30 |

## 4. Интеграция с кассами (ключевое требование)

### 4.1 Принципы

- Контракт задаёт ИИ-официант, а не касса. Любая касса подключается коннектором, который переводит её данные в формат Integration API и обратно.
- Касса — единственный источник правды по позициям и ценам. У нас хранится копия для быстрой работы.
- Коннектор сам соединяется с ИИ-официантом, связь всегда исходящая от коннектора. Кассу и локальную сеть заведения не нужно открывать в интернет.
- Ядро не содержит кода, специфичного для кассы.

### 4.2 Виды коннекторов

| Вид | Где работает | Пример |
|---|---|---|
| Встроенный в кассу | модуль внутри кассовой программы, запуск по cron | «restoran» (Yii2), см. приложение A |
| Облачный | отдельный сервис, связывает облачный API кассы с Integration API | кассы с облачным API (iiko, Poster и т.п.) |
| Локальный агент | небольшая программа на компьютере заведения, работает с локальным интерфейсом кассы | кассы без облачного API (r_keeper и т.п.) |
| Файловый импорт | встроен в ядро | загрузка меню из CSV/XLSX вручную или по расписанию |

Какой вид нужен для конкретной кассы, решается при подключении заведения.

### 4.3 Возможности коннектора

При регистрации коннектор объявляет свои возможности, и ядро подстраивает поведение под них.

| Возможность | Если есть | Если нет |
|---|---|---|
| `menu` (обязательная) | меню и цены приходят из кассы | — |
| `stoplist` | стоп-лист из кассы | ручной переключатель в админке |
| `tables` | столы кассы приходят для сопоставления | `external_id` стола вводится вручную или не используется |
| `push_order` | подтверждённый заказ автоматически уходит в кассу | официант вбивает заказ в кассу сам |
| `order_status` | касса сообщает о закрытии счёта, визит закрывается, гостю предлагается оценка | визит закрывает официант |

### 4.4 Integration API (v1)

Базовый путь `/integration/v1`. Авторизация — `Authorization: Bearer {connector_key}`. Ключ выпускается в админке платформы, хранится в БД только в виде хеша и привязан к одному заведению (`tenant_id` определяется по ключу). Формат — JSON, деньги передаются строкой с двумя знаками после запятой (`"12.50"`).

| Метод | Назначение |
|---|---|
| `POST /hello` | Коннектор сообщает тип, версию и возможности; в ответ получает настройки (интервалы опроса). |
| `PUT /menu` | Полный снимок меню: категории и позиции. Позиции, которых нет в снимке, скрываются (не удаляются). |
| `PUT /stoplist` | Полный список `external_id`, которых нет в наличии. |
| `PUT /tables` | Столы кассы: `external_id`, название, зал. |
| `GET /orders?status=confirmed&after={cursor}` | Подтверждённые официантом заказы, ещё не принятые кассой. Возвращает `next_cursor`. |
| `POST /orders/{order_id}/ack` | Касса приняла заказ (`pos_ref` — номер чека в кассе) или вернула ошибку (`error`). Повторный вызов с теми же данными ничего не меняет. |
| `POST /orders/{order_id}/closed` | Счёт по визиту закрыт в кассе (при возможности `order_status`). |
| `POST /heartbeat` | Коннектор жив; в ответе — нужна ли принудительная синхронизация. |

Пример позиции в `PUT /menu`:

```json
{
  "external_id": "157",
  "category_external_id": "19",
  "name": "Dolma",
  "prices": {"default": "8.00", "vip": "10.00"},
  "currency": "AZN",
  "station": "Metbex",
  "sort_key": "17003",
  "is_available": true
}
```

Пример заказа в `GET /orders`:

```json
{
  "order_id": "5f1c…-uuid",
  "table_external_id": "12",
  "price_tier": "vip",
  "confirmed_by": {"staff_id": 7, "pos_user_ref": "4"},
  "confirmed_at": "2026-10-01T19:42:10+04:00",
  "items": [
    {"external_id": "157", "qty": "2", "price": "10.00", "comment": "без лука"}
  ],
  "total": "20.00",
  "currency": "AZN"
}
```

### 4.5 Правила синхронизации

- INT-1. Меню и стоп-лист коннектор отправляет полным снимком раз в `menu_sync_interval` (по умолчанию 5 мин) и по кнопке «синхронизировать сейчас» (флаг в ответе `heartbeat`). Если снимок не изменился (по хешу), ядро ничего не пересчитывает.
- INT-2. Позиции связываются по `external_id`. Позиции, пропавшие из кассы, скрываются, но не удаляются: сохраняются старые заказы и данные, введённые админом.
- INT-3. При отправке заказа цена перепроверяется по последнему снимку. Если она изменилась с момента добавления в корзину, гость видит уведомление и подтверждает новую сумму.
- INT-4. Если коннектор не выходит на связь дольше `menu_stale_alert_min`, гость видит последнее меню, заказы принимаются (они идут официанту), админу уходит алерт.
- INT-5. Заказы коннектор забирает опросом раз в 3–5 секунд. Доставка «как минимум один раз»: коннектор обязан быть идемпотентным по `order_id`, чтобы повторная выдача не создала заказ в кассе дважды.
- INT-6. Если касса вернула ошибку в `ack`, заказ получает статус `pos_failed`, официант видит это в панели и вбивает заказ вручную.
- INT-7. Если касса посчитала сумму иначе (`ack` содержит `pos_total`), расхождение записывается и показывается админу. Цель метрики — ноль расхождений.

### 4.6 Жизненный цикл заказа

```
submitted ──► confirmed ──► sent_to_pos ──► in_pos
   │  ▲           │                          │
   │  └ edited    │                          └──► (визит закрыт)
   ├──► rejected  └──► pos_failed ──► (официант вводит вручную)
   └──► escalated ──► confirmed / rejected
```

Без возможности `push_order` заказ после `confirmed` остаётся в этом статусе, официант вбивает его в кассу сам.

## 5. Поведение ИИ

- AI-1. ИИ не хранит меню в промпте целиком и не выдумывает данные. Он вызывает функции (tool calling): `get_menu(category?)`, `search_menu(query, filters)`, `get_dish(id)`, `cart_add/remove/update`, `cart_view`, `call_waiter(reason)`, `request_review`. Цены и составы приходят только из ответов этих функций. Функции отправки заказа у ИИ нет: заказ уходит только по кнопке гостя (FR-6).
- AI-2. Аллергены и диета: отвечаем только по блюдам с флагом «аллергены проверены». Без флага честно говорим, что не знаем, и предлагаем позвать официанта. Для аллергиков обязательна оговорка «уточните у официанта». Это защита от вреда здоровью и юридический риск.
- AI-3. Границы: бот говорит только про заведение, меню и заказ. Не обсуждает политику, не выполняет посторонние просьбы, не раскрывает системный промпт. Защита от prompt injection: сообщения гостя и описания блюд считаются данными, не инструкциями.
- AI-4. Передача человеку: при жалобе, споре по счёту, сложном вопросе, повторном непонимании бот автоматически вызывает официанта.
- AI-5. Не даёт скидок и не обещает то, чего нет в данных (акции, время приготовления, наличие).
- AI-6. Языки: AZ и RU; при смешанной речи отвечает на языке последнего сообщения. Качество азербайджанского проверяется на тестовом наборе диалогов до выбора модели.
- AI-7. Лимиты из раздела 3.4, чтобы не сжечь бюджет и не получить злоупотребление.
- AI-8. Модель и её параметры задаются в конфигурации, а не в коде: смена модели не требует релиза.

## 6. Нефункциональные требования

- NFR-1. Время ответа: первый токен в чате до 2 с, ответ стримится (SSE). Если ИИ вызывает функции, гость сразу видит индикатор «подбираю…».
- NFR-2. Мобильный интерфейс в приоритете (99% гостей на телефоне), без установки, быстрая загрузка на слабом интернете.
- NFR-3. Надёжность заказа: заказ сохраняется в БД до любого вызова ИИ и не зависит от сбоя модели. Идемпотентность отправки: двойное нажатие даёт один заказ (ключ идемпотентности генерируется на клиенте).
- NFR-4. Безопасность: непредсказуемые отзываемые токены столов, rate-limit по IP и столу, только HTTPS, `tenant_id` во всех запросах и проверка доступа по нему, ключи коннекторов хранятся хешем, секреты в переменных окружения, а не в коде.
- NFR-5. Персональные данные: минимум. Гость анонимен, регистрации нет. Диалоги хранятся `dialog_retention_days` и без привязки к личности.
- NFR-6. Наблюдаемость: структурированные логи, трассировка вызовов ИИ и функций, метрики (доля успешных заказов, вызовы официанта, стоимость диалога, задержка синхронизации).
- NFR-7. Стоимость: целевая цена ИИ на один визит определяется по тестам; ориентир — от долей цента до нескольких центов.
- NFR-8. Переносимость: система запускается одинаково на сервере заведения и на VPS (раздел 9). Нет привязки к ОС, локальным путям и адресам локальной сети.
- NFR-9. Резервные копии: ежедневный дамп БД и медиафайлов, хранится вне сервера (минимум 7 дневных копий). Восстановление проверено до запуска.

## 7. Модель данных (PostgreSQL)

Во всех таблицах заведения есть `tenant_id`. Деньги хранятся как `NUMERIC(10,2)`, время — `timestamptz`.

**Платформа и заведение**
- `tenants` — заведение: название, валюта, часовой пояс, языки, настройки (`jsonb`, пороги из 3.4, правила бота).
- `halls` — залы.
- `tables` — hall_id, название, тип (стол/кабинет), `price_tier`, `external_id` (стол кассы), `qr_token` (уникальный), `token_issued_at`, `is_active`.
- `staff_users` — роль (официант/админ), логин, `pin_hash`, `password_hash`, `telegram_chat_id`, `pos_user_ref` (пользователь в кассе).
- `connectors` — тип, версия, `key_hash`, возможности, `last_seen_at`, `last_menu_sync_at`, `last_menu_hash`, `last_error`.

**Меню**

## 8. Стек

**Backend: Python 3.12 + FastAPI.**
- SQLAlchemy 2 (async) + Alembic — работа с БД и миграции.
- Pydantic — схемы запросов и ответов, автоматическая документация OpenAPI для Integration API.
- PostgreSQL 16 — основная БД.
- Redis — pub/sub событий для панели официанта, rate-limit, очередь фоновых задач. **Необязателен** (см. ниже).
- arq — фоновые задачи (эскалации по таймеру, алерты, очистка старых диалогов, импорт файлов).

**Два режима работы backend** (выбираются переменной окружения, код один):

| Компонент | Режим `single` (пробный запуск на Windows) | Режим `scaled` (VPS, Docker) |
|---|---|---|
| Шина событий для WebSocket | в памяти процесса | Redis pub/sub |
| Фоновые задачи | планировщик внутри процесса (APScheduler) | arq-воркер на Redis |
| Rate-limit | в памяти процесса | Redis |
| Процессы | один процесс uvicorn | несколько процессов api и отдельный worker |

Код приложения обращается только к интерфейсам `EventBus`, `TaskScheduler` и `RateLimiter`; реализация подставляется по конфигурации. Режим `single` рассчитан на одно заведение и один процесс; при переносе на VPS включается `scaled` без изменений кода.
- Anthropic Python SDK — Claude API с tool use и стримингом.

**Frontend: React + Vite + TypeScript (PWA), Tailwind.** Одно приложение с разными маршрутами для гостя (`/t/…`), официанта (`/staff`) и админа (`/admin`).

**Реалтайм:** SSE для стриминга ответов ИИ гостю, WebSocket для панели официанта, Redis pub/sub для рассылки событий. Telegram-бот — резервный канал уведомлений официантам и админу.

**LLM:** Claude API с tool use. Кандидаты для основного диалога — Claude Haiku 4.5 (дешевле и быстрее) и Claude Sonnet 5 (сильнее в азербайджанском). Выбор фиксируется после теста на 30–50 реальных диалогах на AZ и RU (качество, скорость, цена). Системные инструкции кэшируются (prompt caching) для снижения стоимости.

**Коннектор к «restoran»:** PHP, внутри Yii2-программы (приложение A).

**Инструменты:** Docker Compose, Caddy (HTTPS и reverse proxy), GitHub Actions (сборка образов, тесты), Sentry (ошибки).

## 9. Размещение и перенос

### 9.1 Пробный запуск: сервер заведения (без Docker)

Цель — проверить продукт в заведении до оплаты VPS. Сервер: Windows Server 2019 (версия 1809, сборка 17763), обычный компьютер в домене заведения, в одной сети с принтерами; на нём работает OpenServer с кассой; свободно около 21 ГБ.

На Windows Server 2019 нет WSL2, а Docker там запускает только Windows-контейнеры, поэтому ИИ-официант ставится **нативно** в режиме `single` (раздел 8):

```
Телефон гостя ──HTTPS──► домен ──► Cloudflare Tunnel ──► сервер заведения (Windows Server 2019)
                                                          ├─ служба cloudflared
                                                          ├─ служба ai-waiter (Python 3.12, uvicorn, режим single)
                                                          │    └─ статика frontend раздаётся этим же процессом
                                                          ├─ служба PostgreSQL 16 (Windows)
                                                          └─ OpenServer: касса «restoran»
                                                               ├─ задача Планировщика: php yii ai-sync
                                                               └─► принтеры кухни и бара (LAN)
```

- **Доступ из интернета — Cloudflare Tunnel** (служба `cloudflared`, бесплатно). Соединение исходящее: не нужен проброс портов на роутере, нет конфликта с OpenServer за порты 80/443, HTTPS выдаётся автоматически.
- **Нужен домен**, подключённый к Cloudflare (например, `menu.{бренд}.az`). QR-коды печатаются только на домен. Для самой первой проверки без домена можно использовать временный адрес `*.trycloudflare.com`, но он меняется при перезапуске, и печатать QR на него нельзя.
- ai-waiter и `cloudflared` работают как службы Windows (через WinSW или NSSM) с автозапуском. ai-waiter слушает только `127.0.0.1`, снаружи доступен лишь через туннель.
- Коннектор обращается к ИИ-официанту по домену, как будет и после переноса.
- Касса и OpenServer не меняются.

### 9.1a Ресурсы и ограничения пробного запуска

- Нагрузка: один процесс Python (≈300–500 МБ RAM) и PostgreSQL (≈200–300 МБ). Нужно убедиться, что касса не проседает; проверить свободную RAM.
- Диск: 21 ГБ достаточно для пробного запуска. Фото блюд сжимаются при загрузке (до ~200 КБ). Бэкапы не хранить на этом же диске (NFR-9).
- Если в заведении пропадёт интернет, гости не откроют меню. Для пробного запуска это допустимо, для постоянной работы — аргумент за VPS.
- Обновления Windows с перезагрузкой: окно обслуживания вне часов работы, проверка автозапуска служб.

### 9.2 Требования переносимости

- Конфигурация только в переменных окружения (`.env`), одинаковая для нативного запуска на Windows и для Docker.
- На VPS всё запускается одним `docker compose up`; на Windows — служба с тем же приложением.
- Код и зависимости кроссплатформенные: проверяются в CI на Windows и Linux.
- Всё состояние хранится в PostgreSQL и в одном томе с медиафайлами. Другого состояния на сервере нет.
- Никаких абсолютных путей, адресов локальной сети и зависимостей от ОС в коде ядра.
- Медиафайлы хранятся через слой хранения: локальный том в пилоте, S3-совместимое хранилище позже, без изменения кода.

### 9.3 Перенос на VPS

Если пробный запуск себя оправдал:

1. Поднять `docker compose` на Linux VPS, режим `scaled`.
2. Перенести дамп PostgreSQL и папку медиафайлов.
3. Переключить туннель (или DNS) домена на VPS.
4. В коннекторе ничего не менять: адрес тот же, домен.

QR-коды остаются прежними. Службы ai-waiter, PostgreSQL и cloudflared на сервере заведения после переноса отключаются.

## 12. Риски

- Коннекторы других касс: закрытый или платный API. Митигация: локальный агент, файловый импорт, режим без `push_order`.
- Неверный ответ об аллергенах. Митигация: AI-2, флаг «проверено», оговорка, эскалация к официанту.
- Качество азербайджанского. Митигация: тест до выбора модели, запасной вариант — более сильная модель для AZ.
- Официанты не пользуются панелью. Митигация: звук и вибрация, эскалация, Telegram-дубль, обучение.
- Злоупотребление ботом (спам, посторонние темы, накрутка расходов). Митигация: лимиты и rate-limit (AI-7, NFR-4).
- Заказ из-за пределов заведения по сфотографированному QR. Митигация: подтверждение официантом, перевыпуск токенов, при необходимости — открытие визита официантом.
- Сервер заведения недоступен (интернет, питание) или ИИ-официант мешает работе кассы. Митигация: пробный запуск с контролем ресурсов (9.1a), перенос на VPS, резервные копии.
- Освоение нового стека. Митигация: этап 1 одновременно служит обучением; коннектор пишется на знакомом PHP.

## Приложение A: коннектор для Yii2-программы «restoran»

По разбору дампа `restoran(3).sql` (MariaDB 10.3) и кода `restoran/`. Коннектор — модуль внутри программы, реализует возможности `menu`, `stoplist`, `tables`, `push_order`, в перспективе `order_status`.

### A.1 Как устроена касса (установлено по коду)

| Вопрос | Ответ |
|---|---|
| Заведения | В БД одно заведение: один `tenant`, один ключ коннектора. Таблица `type` — категории (типы) меню; префиксы в названиях («Bekmez …», «Babayenin Yeri …») — просто названия разделов меню. Столы и кабинеты хранятся в `place`. |
| Открытые заказы | `sell2` (`sold=0`). Одна группа строк с одинаковым `number` — один заказ стола. |
| Закрытые заказы | `sell`. При закрытии счёта `SellController::actionReceived` переносит строки из `sell2` в `sell`, списывает продукты со склада по FIFO (`consist` → `arrival.rest`) и удаляет строки из `sell2`. |
| `postponed` | Отложенный счёт. |
| Номер заказа | Если у стола есть открытый `sell2`, берётся его `number`, иначе `max(sell2.number, sell.number) + 1`. Блокировки нет, возможна гонка. |
| Повтор блюда | Добавление того же `id_menu` на тот же стол увеличивает `quantity` существующей строки. |
| Комментарий к позиции | `sell2.note` (одна строка — один комментарий). |
| Печать на кухню/бар | `actionPrint3`: строки с `print != quantity` уходят через `PrintService` на `store.ip` по станции блюда (`menu.id_store`), затем `print = quantity`. Принтеры в локальной сети. |
| Тариф | Официант выбирает Standart/VIP в начале работы (сессия, `tarif`). При VIP берётся `price_vip`, если он больше 0. Шаг скрывается настройкой `show_vip_standart`. |
| `vid` | Код сортировки: у `type` две цифры, у `menu` код типа плюс три цифры. |
| Валюта | AZN (USD только в приходах от поставщиков). |
| `flag` | «Подтверждён?», в продажах не используется. |

### A.2 Соответствие данных Integration API

| Integration API | Касса |
|---|---|
| категория: `external_id`, `name`, `sort_key` | `type.id`, `type.name`, `type.vid` |
| позиция: `external_id`, `name`, `sort_key`, `station` | `menu.id`, `menu.name`, `menu.vid`, `store.name` через `menu.id_store` |
| `prices.default` / `prices.vip` | `menu.price` / `menu.price_vip` (если больше 0, иначе `vip` не передаётся и берётся `default`) |
| `is_available` | `menu.disabled = 0` |
| стол: `external_id`, `name`, зал | `place.id`, `place.name`, `type_place.name` |
| `confirmed_by.pos_user_ref` | `users.id_user` официанта, указанный в его профиле ИИ-официанта |

Цены в кассе хранятся во `float`; коннектор округляет их до 2 знаков.

### A.3 Изменения в программе «restoran»

1. **`OrderService`** — вынести из `SellController` логику, не зависящую от сессии:
   - `addItems(int $placeId, int $userId, string $tier, array $items): int` — добавить позиции в открытый заказ стола, вернуть `number`. Номер выдаётся в транзакции с блокировкой (`SELECT … FOR UPDATE`), чтобы убрать гонку.
   - `printPending(int $placeId): array` — отправить непечатанные строки на принтеры.
   - Экшены `actionIndex`, `actionInsert`, `actionPrint3` переводятся на этот сервис, поведение кассы для официанта не меняется.
2. **Позиции с комментарием не сливаются**: если у новой позиции есть комментарий, создаётся отдельная строка `sell2` с `note`, иначе действует прежнее правило.
3. **Строки заказа записываются на официанта, подтвердившего заказ** (`confirmed_by.pos_user_ref`), а не на служебного пользователя. Так официант может отменять и править их со своего экрана, как обычно.
4. **Таблица `ai_order_map`** (единственная новая таблица, Yii2-миграция) — для идемпотентности:
   ```sql
   CREATE TABLE ai_order_map (
     order_id CHAR(36) NOT NULL PRIMARY KEY,   -- order_id из Integration API
     number INT NOT NULL,                      -- sell2.number
     created_at DATETIME NOT NULL
   );
   ```
   Если `order_id` уже есть в таблице, коннектор не создаёт заказ повторно, а сразу повторяет `ack`.
5. **Консольная команда `php yii ai-sync`** (cron каждую минуту, внутри цикл до 60 с):
   - раз в `menu_sync_interval` отправляет `PUT /menu`, `/stoplist`, `/tables` (и сразу, если `heartbeat` просит синхронизацию);
   - каждые 3–5 с забирает `GET /orders`, для каждого заказа в одной транзакции вызывает `OrderService::addItems` и пишет `ai_order_map`, затем `printPending` и `ack` с `pos_ref = number` и `pos_total`;
   - при ошибке отправляет `ack` с `error`;
   - блокировка от параллельного запуска (mutex).
6. **Настройки коннектора** в таблице `settings`: адрес Integration API, ключ коннектора, интервал синхронизации.
7. **Возможность `order_status` (позже):** в `actionReceived` после закрытия счёта, если у `number` есть запись в `ai_order_map`, коннектор отправляет `POST /orders/{id}/closed`.

### A.4 Что нужно исправить в кассе до выхода в прод

- Пароль в таблице `password` хранится открытым текстом — хешировать.
- `YII_ENABLE_ERROR_HANDLER = false` и отладочный вывод (`print_r`, `var_dump`) в `SellController` — убрать из путей, которые вызывает коннектор.

2. Названия в `menu.name` — латиница, до 20 символов, русских названий нет. Кто заполнит `name_az`/`name_ru` в админке ИИ-официанта?
